# 앱 디자인 점검

목표는 "AI가 만든 앱 같다"는 인상을 없애고, 모든 조작이 눈에 보이는 결과와 설명을 갖게 하는 것이다. 색, 글꼴, 브랜드는 앱마다 정하는 입력값이며 이 스킬에 기본 스타일은 없다. 사용자가 이미 정한 디자인 방향이 있으면 그것이 우선이다.

## 절차

1. **모든 화면 찍기:** 실행 인수로 모든 화면과 주요 상태를 열어 찍는다(ios-verify-harness 스킬). 빈 상태, 처리 중, 오류, 결과 화면도 포함한다. 라이트·다크, 가장 작은 기기, 가장 긴 언어를 한 번씩 넣는다.
2. **신호 찾기:** [references/slop-tells.md](references/slop-tells.md)의 목록으로 화면마다 걸리는 항목을 적는다. 막연히 "세련되게"가 아니라 "카드 9개가 같은 반경·그림자", "아이콘 원형 배지 14개"처럼 센다.
3. **상호작용 점검:** [references/interaction-honesty.md](references/interaction-honesty.md)대로 주요 버튼·프리셋·토글을 직접 눌러 결과가 보이는지, 다시 누르면 무엇이 되는지, 무엇을 했는지 말해 주는지 확인한다.
4. **디자인 계획:** 고치기 전에 한 파일(예: `Theme.swift`)에 토큰을 정한다.
   - 색: 4~6개 이름 있는 색
   - 글꼴 역할: 제목, 본문, 숫자
   - 간격 단계, 모서리 반경 단계
   - 반복 컴포넌트: 탭, 슬라이더, 도구 목록, 기본 버튼

   앱의 주제에서만 나올 수 있는 디테일을 하나 정한다. 예: 피부톤 앱이면 실제 피부색 15단계 띠를 유일한 색으로 쓰고 나머지는 무채색으로 둔다.
5. **다시 짜기:** 화면 코드가 색·크기 상수를 직접 쓰지 않고 토큰과 컴포넌트만 쓰게 바꾼다. 콘텐츠(사진, 결과물)가 화면의 주인공이 되도록 장식을 걷어 낸다.
6. **전후 비교:** 같은 화면을 다시 찍어 전후를 나란히 놓고, 사용자에게 보여 준다(맥에서 이미지를 열어 주거나 비교 시트를 만든다). 취향이 갈리는 결정(기본 프리셋 강도, 대표 효과, 색)은 후보 2~3개를 나란히 렌더해 고르게 한 뒤에 기본값을 바꾼다.

## 지켜야 할 것

- 사용자가 거절한 스타일은 기록하고 다시 쓰지 않는다. 예: 크림색 배경 + 세리프 + 테라코타, 아이콘 배지 칩.
- 요청받지 않은 출구와 요청을 붙이지 않는다. 공유·SNS 버튼, 별점 요청 버튼, 마케팅 수신 동의, 실행 광고 같은 것들이다. 저장만 원하면 저장만 둔다.
- 제목·버튼 문구는 마침표 없이 짧게 쓴다(design-punctuation 스킬). 문구는 사용자가 아는 말로, 기능이 실제로 하는 일을 쓴다.
- 접근성: 탭 영역 44pt 이상, Dynamic Type, 대비, VoiceOver 라벨을 함께 확인한다.
- 디자인을 바꾼 뒤에도 자가 점검과 스크린샷을 다시 돌려 기능이 깨지지 않았는지 확인한다.
