# glance-and-guardrails

기능이 돌아간 뒤에 오는 피드백은 거의 둘이다. "뭘 먼저 봐야 하지"와 "실수로 지우면 어떡하지". 둘 다 패턴이 있다.

## 입력
- 사용자의 제품 피드백 문장 그대로(예: "밋밋하다", "137개 항목이 다 보여서 못 읽겠다").
- 데이터에서 "주의"를 결정하는 기준 — 반드시 **원천에 적힌 표시**에서만(앱이 판단을 만들지 않음, 헌법 확인).

## 절차 — 한눈에 보기
1. **레퍼런스 3곳** — 같은 문제를 푼 서비스 셋을 WebSearch로 찾고 공통 패턴만 적는다(예: 범위 밖 개수부터, 신호등 한 점, 참고 범위 막대 + 내 값, 나머지 접기).
2. **목업** — Artifact로 케이스별(정상/주의/위험/기록 없음) 화면 1장. **가상 데이터**로.
3. **구현** — `glance()` 같은 순수 함수 하나가 점 단계·문장·개수를 만든다. 목록은 SHOW=3 + "N개 더 보기"(`<details>`). 색 토큰은 의미당 하나(ok/warn/danger + soft).
4. 홈 목록도 같은 함수로 한 줄씩: 점 + 이름 + 개수 문장.

## 절차 — 안전장치
5. **확인 모달** — 삭제·탈퇴·로그아웃은 `<dialog>` 확인 버튼 컴포넌트 하나로 통일. 서버 액션은 그대로.
6. **남용 상한** — 잔액 컬럼이 아니라 원장(delta 합계). 차감 RPC는 advisory lock, 가입 트리거로 초기 크레딧. 환불은 결제가 생길 때.
7. 각각 `ship-loop`로 PR.

## 멈추는 지점 (사람 몫)
- 크레딧 수치(가입 N회), 무엇을 "주의"로 볼지의 최종 기준, 목업 승인.

## 산출물
한눈에 보기 화면, 확인 모달 컴포넌트, 크레딧 원장. 다음 단계는 `env-split`.
