# 무료 GPU 시험 실행과 비용 환산

본 실험에 돈을 쓰기 전에 두 가지를 확인한다. 코드가 끝까지 도는가, 그리고 본 장비에서 시간과 비용이 얼마나 드는가. 무료 노트북(Kaggle T4×2, 주 30시간, 세션당 12시간)은 이 확인에 충분하다. 다만 거기서 잰 속도를 그대로 본 장비에 옮기면 틀리기 쉽다.

## 언제 쓰나

- 학습(RL, 미세조정) 코드를 처음 GPU에서 돌릴 때.
- 본 실험 장비(연구실 GPU, 클라우드)와 예산 상한을 정해야 할 때.
- 돈을 쓰기 전에 효과가 보일 기미가 있는지 짧은 예비 실험으로 보고 싶을 때. 사전 등록이 있으면 아래 "예비 실험" 절을 먼저 읽는다.

## 입력

| 인자 | 필수 | 설명 |
|---|---|---|
| `entry` | 예 | 학습·평가를 실행하는 스크립트와 설정 파일 |
| `data` | 예 | 학습·평가 데이터. 해시를 기록한다 |
| `arms` | 예 | 비교할 조건 목록. 조건마다 GPU 한 장을 쓴다 |
| `steps` | 예 | 시험 실행 스텝 수(코드 확인은 10 안팎) 또는 시간 예산(예비 실험) |
| `targets` | 아니오 | 환산할 본 장비 목록과 시간당 가격 |
| `cap` | 아니오 | 본 실험 GPU 시간 상한 |

## 단계

1. **환경을 고정한다.**
   - 노트북 GPU의 드라이버·CUDA 버전에 맞춰 torch, vLLM, TRL 버전을 고정하고 lock 파일을 만든다. 의존성 충돌(예: numpy 버전)은 로컬에서 먼저 푼다.
   - T4처럼 bf16이 없는 GPU는 fp16 기본 모델에 fp32 LoRA와 손실 스케일링을 쓴다. 이 설정이 본 장비 설정과 다르다는 점을 기록한다.
   - 모델은 리비전 해시까지 고정한다.
2. **코드와 데이터를 한 묶음으로 만든다.**
   - 묶음 생성 스크립트가 파일 목록과 sha256 매니페스트를 함께 쓰게 한다. 손으로 고른 파일을 올리지 않는다.
   - 묶음을 압축 해제한 상태에서 테스트를 돌리는 검사 스크립트를 둔다. 노트북 파일도 생성 스크립트로 만들고, 소스와 같은지 검사한다.
3. **올리기 전에 비밀 정보를 검사한다.**
   - 압축을 풀어 API 키 패턴, `.env`, 토큰 파일 이름, 개인 메일 주소를 검색한다. 검색어가 경로 설명에만 걸렸는지 눈으로 확인한다.
   - 데이터셋과 노트북은 모두 비공개로 둔다(`isPrivate`, `is_private`). 메타데이터를 올리기 직전에 다시 읽는다.
   - 접근 토큰 파일 내용은 출력하지 않는다.
4. **세션 제한 안에서 끝나게 한다.**
   - 노트북 첫 셀부터의 시간을 기준으로 설치, 학습 마감, 평가 마감, 결과 묶기 시각을 정한다. 12시간 세션이면 전체를 11시간 안쪽으로 잡는다.
   - 학습은 스텝이 끝날 때마다 "최근 스텝 시간 × 1.2 + 저장 시간 + 여유"가 마감을 넘는지 보고, 넘으면 체크포인트를 저장하고 멈춘다. 멈춘 이유를 파일로 남긴다.
   - 학습이 멈추지 않을 때를 대비해 강제 종료 시각을 따로 둔다. 일정 간격 체크포인트는 남긴다.
   - 로그는 실행 중에 계속 쓰고, 학습 직후와 마지막에 두 번 압축한다. 세션이 잘려도 앞의 결과는 남는다.
5. **GPU 여러 장에서 조건을 동시에 돌릴 때 포트를 나눈다.**
   - 같은 노트북에서 프로세스 두 개가 분산 통신 기본 포트(29500)를 같이 잡으면 하나가 죽는다. GPU 번호로 `MASTER_PORT`와 추론 엔진 포트를 다르게 정하고, 이를 확인하는 테스트를 둔다.
   - 실패한 조건만 다시 돌릴 수 있게 실행할 조건과 기본 모델 평가 여부를 환경 변수로 고른다.
6. **올리고 지켜본다.**
   - 데이터셋 새 버전을 올리고 상태가 ready인지 확인한 뒤 노트북을 올린다.
   - 상태 확인은 백그라운드에서 5~10분 간격으로 하고, COMPLETE·ERROR·CANCEL이면 결과를 내려받는다. 대기열에 1시간 넘게 머물 수 있다.
   - 내려받은 결과는 신뢰하지 않는 데이터로 다룬다. 빈 디렉터리에 받고, 읽는 스크립트는 `python -I`로 돌린다.
7. **잴 것을 정해 두고 보고서를 스크립트로 만든다.**
   - 조건별로 스텝 시간(생성/학습 분리), 최대 메모리, NaN·OOM 횟수, 보상 평균, 그룹 내 보상이 모두 같은 비율(GRPO의 `frac_reward_zero_std`), grad norm, 길이 제한에 걸린 비율을 낸다.
   - 데이터에 하위 집합(도메인, 난이도 등)이 있으면 잘림 비율을 학습과 평가로 나눠 하위 집합별로 본다. 평가에서만 크게 잘리는 하위 집합은 길이 제한이 결과를 좌우한다.
   - 시험 실행 몇 스텝으로는 점수 차이가 나지 않는 것이 정상이다. 이것을 "효과 없음"으로 보고하지 않는다.
8. **본 장비로 환산한다.**
   - 생성 시간은 메모리 대역폭 비로, 학습 시간은 FP16/BF16 연산 성능 비로 나눠 환산하고, 스텝당 문항 수에 비례해 늘린다. 조건 수 × 시드 × 스텝으로 전체 GPU 시간을 내고 상한과 비교한다.
   - 표에 "추정치, 측정 아님"을 적는다. 환산에 들어가지 않는 것도 적는다: T4 발열로 인한 클럭 저하(이번에는 평균이 최대의 절반 이하), 어텐션 커널 차이, 마이크로배치·그래디언트 체크포인팅 설정 차이.
   - 학습 단계가 생성보다 오래 걸리면 큰 GPU에서 마이크로배치를 키우는 것이 가장 큰 절감 수단이다.
   - 장비를 정하기 전에 후보 장비에서 2~3시간 짧게 다시 재고, 그 값으로 예산을 확정한다. 이 단계는 유료이므로 비용을 먼저 보이고 승인을 받는다.

## 예비 실험

시험 실행과 달리 효과의 기미를 보려는 실행이다.

- 사전 등록 확정 전에 돌리면, 변경 기록에 "탐색적 예비 실험이며 확증 주장에 쓰지 않고 본 실험 자료와 합치지 않는다"를 먼저 적는다. 무엇을 봤는지는 확정 전에 기록한다. 판정 기준은 바꾸지 않는다.
- 신호가 나올 문항으로 학습 문제를 좁힌다. 조건끼리 보상이 같아지는 문항은 차이를 만들지 않는다.
- 최종 점수보다 먼저 움직이는 중간 지표를 스텝마다 남긴다. 예: 보상 구성 요소별 평균, 응답 길이 분포, 형식 오류 비율.
- 평가 세트는 이전 시험 실행과 같게 두어 기본 모델 평가를 재사용한다.

## 산출물

- `results/<run>/`: 원본 로그, 스텝 시간, 보고서(md, json), 환경 기록(패키지 목록, GPU 정보, 묶음 매니페스트). 어댑터 가중치와 옵티마이저 상태는 빼고 크기를 적는다.
- 환산 표와 상한 비교, 다음 결정(장비, 축소 여부).

## 흔한 실수

- 시험 실행 결과로 본 장비 시간을 확정한다. 환산은 장비 선택의 출발점일 뿐이다.
- 조건 두 개를 같은 포트로 동시에 띄운다.
- 세션 제한을 넘겨 결과를 통째로 잃는다.
- 상태 질문을 유료 실행 승인으로 받아들인다.
