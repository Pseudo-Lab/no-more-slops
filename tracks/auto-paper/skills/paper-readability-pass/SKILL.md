# 논문 가독성 점검 루프

새 결과가 들어오거나 마일스톤 직전에 한 번씩 돌린다. 목표는 처음 읽는 사람이 초록과 서론만 읽고 "무엇을 했고 무엇을 찾았는지"를 한 문장으로 말할 수 있게 하는 것이다.

이 스킬은 글의 읽기 쉬움만 다룬다. 원고의 숫자가 결과 파일과 맞는지, 인용이 원문과 맞는지, 실험이 더 필요한지는 판정하지 않는다. 그런 지적이 나오면 기록만 하고 해당 작업을 맡은 스킬이나 사람에게 넘긴다.

## 입력

| 인자 | 필수 | 설명 |
|---|---|---|
| `pdf` | 예 | 빌드된 원고 PDF 경로 |
| `source` | 예 | 원고 소스 폴더(LaTeX 등). 3단계에서 고칠 대상 |
| `venue` | 예 | 투고처와 트랙. 예: 어느 학회의 short paper |
| `page_limit` | 예 | 본문 쪽수 제한. 참고문헌·Limitations 등 제외 항목은 투고처 규정을 따른다 |
| `structure` | 아니오 | 채택 논문 구조 분석 파일 경로. 없으면 1단계에서 이 경로에 만든다 |
| `review_out` | 예 | 이번 회차 리뷰를 쓸 경로. 예: `reviews/roundN.md`. 이전 회차 파일은 덮어쓰지 않는다 |
| `protected` | 아니오 | 작성자가 손대면 안 되는 파일 목록. 예: 스크립트로 생성한 수치 매크로, 표 파일, 그림 |
| `log` | 아니오 | 회차별 점수와 핵심 지적을 남길 곳(파일, 대시보드 등) |

필수 인자가 빠졌으면 묻는다. 비슷한 이름의 파일을 찾아 대신 쓰지 않는다.

## 역할

각 역할은 사람이 맡아도 되고, Claude Code 서브에이전트로 돌려도 된다. 서브에이전트로 돌릴 때는 역할마다 읽을 수 있는 파일을 아래처럼 제한한다.

| 역할 | 읽는 것 | 쓰는 것 |
|---|---|---|
| 구조 분석 담당 | 채택 논문, `pdf` | `structure` |
| 새 리뷰어 | `pdf` 하나 | `review_out` |
| 작성자 | `pdf`, `source`, `structure`, `review_out` | `source` (`protected` 제외) |
| 메인 세션 | 전부 | 렌더링 확인 결과, `log` |

새 리뷰어는 매 회차 새로 띄운다. 이전 리뷰, 작성 과정, 대화 기록을 넘기지 않는다.

## 단계

1. **구조 기준 확보 (구조 분석 담당, `structure`가 없을 때 한 번만)**
   - 같은 투고처·같은 분량의 채택 논문 5~6편을 읽는다. 공식 논문집이나 저자 공개본에서 확인한 것만 쓴다.
   - 논문마다 기록할 것: 제목 형식, 초록 문장별 역할과 숫자 수, 서론 단락별 역할과 첫 문장 유형, 공백(gap) 문장의 위치, 그림 1의 역할, 새 용어 수, 결과 소제목 형식, 결과 단락의 숫자 수, 유보 표현의 위치와 횟수, 섹션별 분량.
   - 채택 논문의 공통 패턴을 표 하나로 묶는다.
   - 우리 원고를 같은 항목으로 진단하고, 차이가 큰 항목부터 서론·초록 골격을 제안한다. 제목처럼 사람이 정할 것은 선택지만 낸다.
2. **새 리뷰어의 가독성 심사 (새 리뷰어, 매 회차 새로)**
   - `pdf` 한 파일만 읽힌다.
   - 반드시 묻는 것:
     - 초록과 서론만으로 한 문장 요약이 되는가. 되면 그 문장을 직접 써 달라.
     - 걸리는 곳을 줄 번호로 짚어 달라: 정의 없는 용어, 같은 대상의 여러 이름, 모호한 문장, 한 문장·한 단락에 너무 많은 정보, 이 분야 논문에서 보기 어려운 낯선 단어, AI가 쓴 것처럼 읽히는 문장, 가리키는 대상이 불분명한 지시어.
     - 그림과 표가 본문 없이 이해되는가. 그림·표마다 yes/부분/no로 답해 달라.
     - `venue`의 채택 논문 대비 구성이 자연스러운가.
     - 지적을 "글로 고칠 것"과 "실험이나 분석이 필요한 것"으로 나눠 우선순위를 매겨 달라.
   - 결과를 `review_out`에 쓴다.
3. **글만 고친다 (작성자)**
   - `protected`에 있는 파일과 숫자는 건드리지 않는다. 표 열 이름이나 행 묶음을 바꾸려면 그 표를 만드는 스크립트를 고쳐 다시 생성하도록 담당자에게 요청한다.
   - "실험이나 분석이 필요한 것"으로 분류된 지적은 고치지 않고 다음 회차 입력과 담당자 목록에 넘긴다.
   - 점검 기준:
     - 새 용어는 4개 안팎으로 하고, 같은 대상에는 한 이름만 쓴다. 그림 상자, 표 머리, 본문의 이름을 맞춘다.
     - 초록은 문제 → 공백 → 방법 → 결과 1~2개 → 함의 순서로 쓰고, 숫자는 핵심 1~3개만 넣는다.
     - 서론 첫 단락은 구체 장면이나 널리 받아들여지는 전제로 시작하고, 예시는 1쪽 안에 보인다.
     - 구현 세부(호출 경로, 판정 방식 등)는 서론이 아니라 설정 절에 둔다.
     - 유보 표현은 결과 절 한 단락과 Limitations에만 둔다. 다만 결과 해석을 바꾸는 핵심 유보는 Limitations에만 숨기지 말고 결과 절에 한 번 쓴다.
     - 실험 조건은 설정 절의 목록이나 표 하나에서 정의하고, 이후에는 같은 이름만 쓴다.
     - 결과 소제목은 발견 문장으로 쓰고, 단락 첫 문장은 말로 된 주장, 그 뒤에 대표값 1~3개를 둔다. 전체 수치는 표에 맡긴다.
     - 결론은 증거 범위 안의 실무 권고로 끝낸다.
     - 용어는 같은 분야 채택 논문이 실제로 쓰는 말을 쓴다. 용어마다 채택 논문의 표현과 출처(arXiv ID와 절)를 표로 남기고, 만들어 낸 말이나 어색한 연어는 표준 표현으로 바꾼다.
     - AI가 쓴 티가 나는 문장을 고친다: 'Notably', 'crucially' 같은 강조 부사, "not X but Y" 틀, 콜론 뒤 반전, em-dash 삽입구, 한 문장에 숫자 3개 이상.
     - 지시어(this, these, it, the latter)가 무엇을 가리키는지 바로 알 수 없으면 명사로 바꾼다. 한 단락에 지시어로 시작하는 문장이 둘 이상이면 줄인다.
   - `page_limit`을 지킨다.
   - 고친 뒤 `python3 scripts/count_terms.py <source>/main.tex`로 초록 숫자 수·문장 수와 서론의 `\emph`·`\textit` 새 용어 수를 위 기준과 비교한다(벗어나면 종료 코드 1).
4. **렌더링 확인 (메인 세션)**
   - `pdftoppm -r 100 -png <pdf> <prefix>`처럼 PDF를 쪽 이미지로 바꿔 직접 본다. 텍스트 추출만으로 판단하지 않는다.
   - 확인할 것: 표가 단 너비를 넘지 않는지, 그림 상자의 글자가 넘치거나 잘리지 않는지, 행·열 이름이 어색하게 줄바꿈되지 않는지, 표·그림 글자가 읽을 만한 크기인지, 본문이 끝나는 쪽과 위치.
   - 이미지를 보기 전에 `python3 scripts/check_build.py <빌드 폴더> --page-limit <page_limit> --src <source>`로 본문 끝 라벨(기본 `sec:end-of-body`)의 쪽, Overfull/Underfull 경고 위치, 정의 안 된 참조·인용, `h` float 변경, TODO·개인 절대경로 잔존을 JSON으로 확인한다(문제 있으면 종료 코드 1).
   - 깨진 곳을 고치고 다시 빌드한 뒤 같은 쪽을 다시 본다.
5. **기록 (메인 세션)**
   - `log`가 있으면 회차, 리뷰 점수, 핵심 지적, 고친 것, 남긴 것을 남긴다.
   - 남은 지적은 다음 회차 입력으로 넘긴다.

## 주의

- 리뷰를 반영하며 유보 문장을 계속 덧붙이면 다시 읽기 어려워진다. 유보는 한 곳에 모은다.
- 리뷰어마다 초록 숫자의 많고 적음에 대한 의견이 반대로 나올 수 있다. 초록에는 핵심 수치 1~3개를 두는 선을 지킨다.
- 한국어 원고와 영어 원고를 함께 관리하면, 어느 쪽이 최신인지 원고 머리에 적는다.
- 익명 심사 원고라면 리뷰 파일과 기록에도 저자를 드러내는 정보를 넣지 않는다.
